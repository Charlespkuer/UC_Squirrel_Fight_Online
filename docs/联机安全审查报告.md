## 2026-10-30 补充：本机全服通知与读取限流

- 全服奖励邮件只能由服务器本机具有数据库写权限的操作者执行 `server/admin-broadcast.js`，没有公开管理 HTTP 接口。指定唯一编号，事务内保存发放记录并给当时有经典存档且未封禁的账号写一封 `announcement` 邮件；相同编号和内容重试不重复写，相同编号不同内容被拒。之后注册的账号不追溯发放。奖励支持金松果（`gold`）、金杯（`cup`）与普通道具（`props`，8/15/40 走前两项）。**奖励不是立即入账**：玩家必须在消息页点开邮件、在弹窗确认「领取」，由 `POST /api/messages/claim` 校验归属后入账，同一封只能领一次（`payload.claimedAt`）；老公告没有 `claimable`，不会被新版领取接口重复发奖。
- 认证后 GET 请求按账号限制每分钟 300 次，减轻读接口滥用。限流在设备和会话验证之后，因此不能消除验证过程的数据库写放大，也不能抵御多账号或分布式攻击；现有 R-03、R-04、R-05 等风险仍须处理。
- 隔离 API 测试 68/68，包含全服金松果重复执行和不同内容复用编号。尚未进行生产部署、真实玩家浏览器观察或大规模发放性能测试。经典渲染测试在既有 `checkDualSaveAndDebugGate` 断言失败，项目入口已记录该历史失败。

## 2026-10-30 补充：注册容量与断线恢复

- 注册在同一 SQLite 写事务中检查现存账号数，达到 `REGISTRATION_LIMIT` 后返回 503；默认 500，设为 0 关闭限制。注销后名额可重用，封禁账号仍计入。500 是暂定运营阈值，并非测得的安全承载量。两次并发争夺最后一个名额的隔离测试只有一个成功。调整环境变量后须重启服务；已部署服务在更新前不受影响。

## 1. 攻击面与审查方法

重点检查了下面几条“从客户端到服务器”的链路：

1. **本地存档/客户端改包**：客户端 `State` 是否可以改本地存档、上传整档、绕过 `rev`？
2. **动作白名单**：每个 `sync/async` 动作的参数、代价、归属、上限、随机数是否都在服务端校验？
3. **战斗编排**：胜负、经验、金币、金杯、积分、掉落、每日次数是否全部由服务端计算？
4. **异步匹配/快照**：能否指定任意对手、旧快照、低等级快照，绕过匹配范围？
5. **幂等/重放**：断线重试、重复 `POST`、旧 `rev`、旧 `Idempotency-Key` 是否会重复发奖？
6. **账号/设备/会话**：注册、登录、恢复码、设备绑定、会话 TTL、代理 IP。
7. **静态资源与部署**：`server/`、`save/`、`docs/`、`.git`、凭据文件是否会通过 HTTP 泄露。
8. **可用性**：免费接口、全量存档写入、日志/战报/消息/房间表是否会无界增长。
9. **客户端渲染**：玩家名、留言、论坛、战报文本是否存在存储型 XSS（会连带偷 token）。

动态复现使用临时 `DATA_DIR` 和 `127.0.0.1` 随机端口；测试账号、存档、探针脚本都在
`out/`（已 gitignore）。没有对线上 `111.229.39.217` 发起攻击性请求。

### 1.1 手机改时钟专项复核（2026-10-29 追加）

**结论：当前版本改手机本地时间不能重复领日常奖励、重置普通商店/天梯商店限购、刷新体力，
也不能重置每日抽奖的免费次数；服务端判断全部走服务器时间，客户端时间只影响界面显示。**

**验证方法**：服务器进程单独启动（临时库、端口 3212），客户端进程把 `Date.now` 分别
前拨 1 天、2 天、3 天、7 天、14 天，然后调用与正常按钮完全相同的 HTTP 接口。

| 场景 | 客户端时钟 | 服务端结果 |
|---|---|---|
| 当天已领每日礼包，再领 | +1 天 | `{ok:false,"msg":"今天的奖励已经领取，明天再来吧！"}`，金松果不变 |
| 小体力药剂当天已买 3 个，再买第 4 个 | +2 天 | `{ok:false,"limited":true,"msg":"小体力药剂今日已达限购3个"}`，`shopPurchases`/`shopPurchaseDate` 仍是服务端当天 |
| 当天免费抽奖 1 次已用完，再抽 | +3 天 | 第二次 `pay:"gold"`（扣 20 金松果），**不是** `free`；`lotteryDate` 仍是服务端当天 |
| 天梯商店账号限购商品（力量永久+1）已买 1 次，再买 | +7 天 | `{ok:false,"该奖励每个账号累计只能兑换 1 次..."}` |
| 天梯商店每周限购商品（技能卷轴×100）已买 1 次，再买 | +14 天 | `{ok:false,"该奖励本周的兑换次数已用完..."}`；`rankPurchaseWeek` 仍是服务端 2026-10-26 |
| 体力耗到 0，再发起随机挑战 | +7 天 | 409 `体力不足（需要 10 点）` |
| 服务端 `/api/health` | 客户端 +7 天 | `date` 仍是服务端当天（2026-10-29），不是客户端未来日期 |

**为什么改手机时间无效**：

1. **动作不携带时间**。`/api/action` 只接收 `{name,args,rev}`（`server/api/state.js`），
   `/api/battle`、`/api/arena/join`、`/api/campaign/*` 同样没有日期/时间字段；HTTP `Date`
   头也不参与判定。客户端无法把“今天是明天”告诉服务端。
2. **执行发生在服务器进程**。动作由 `server/game/store.runOnSave()` 在服务端调用
   `State.claimDaily`/`State.buyProp`/`State.lotteryDraw`/`State.rankBuy`/`State.consumeEnergy`；
   这些函数里的 `Date.now()` 是服务器时钟，`State.localDate()`/`rankWeekKey()` 也取服务器
   日期，不是手机时钟。`store.housekeeping()` 还会在每次动作前用服务端时间跑
   `syncLotteryDay()`，所以免费抽奖也只能按服务端跨日。
3. **日期状态在服务端存档里**。`dailyClaimDate`、`shopPurchaseDate`、`lotteryDate`、
   `rankPurchaseWeek`、`lastEnergyTs`、`buffDate`、`vip.lastDaily` 都由服务端动作写入并在
   下一次动作重新读回；手机改时间不会改到这些字段。
4. **客户端存档没有上行通道**。联机版 `State.save()` 是空操作；`newGame`/`load`/import/
   export/fileWrite 被禁用；`/api/snapshot/sync` 不接受存档正文；`rev` 不一致会 409。
   改本地镜像不能变成服务器进度。
5. **客户端时间只用于显示**。`online.js` 的 `serverNow()`/`drift` 只用于界面和候选缓存
   （例如 `randomCache` 过期判断）；`dailyStatus`、`purchaseStatus`、`energy` 的客户
   端显示可能被手机时间骗到，但点下去仍由服务端拒绝对应动作，随后 `syncState()` 把镜像
   拉回服务端。

**可以骗到的“假象”**：每日礼包/普通商店/天梯商店限购/抽奖免费次数/体力/建筑倒计时/
VIP 剩余时间的**界面状态**，以及少数纯客户端冷却（如候选列表缓存、挑战页刷新计时）。
它们不会发服务器资源。天梯商店与每日抽奖现在已经是服务端动作（`rankBuy`、`lotteryDraw`），
本轮改时钟复现均被服务端拒绝；**不要再把这两项退回客户端扣款/开奖**，否则手机时钟会变成
真漏洞。

**同类风险的防范边界**：

- **必须设服务器时区**。生产 systemd 与部署脚本都设 `TZ=Asia/Shanghai`、`TZ_NAME=Asia/Shanghai`；
  `config.localDate()` 用 `TZ_NAME`，`State.localDate()`/`rankWeekKey()` 依赖进程 `TZ`。
  若运维漏设 `TZ`，两者可能在不同时区边界重置（每日次数与商店/每日礼包/抽奖/周限购不同步）。
  建议启动时显式校验/记录这两个变量。
- **服务器时钟要用 NTP**。如果宿主时间被管理员/虚拟化平台回拨，`dailyClaimDate` 可能回到
  前一天，从而允许再领一次；这不是手机改时间能触发的，但属于同一类“时间权威”问题。
- **客户端冷却不是安全边界**。`opponentRefreshCooldownMs` 目前只返回给客户端、服务端没有
  执行；改时钟或改客户端可以绕过候选刷新等待。它不直接产资源，但会加快选目标；若要防
  “刷候选”，应在服务端按账号做冷却。
- **师徒日供等仍未接入的功能**不要在服务端接好前恢复本地结算；当前保留的是“暂未开放”分支。

## 2. 已修复问题

### F-01 静态目录黑名单可被 Windows 反斜杠绕过（高）

**位置**：`server/index.js` 的 `serveStatic` / `denyPath`。

**问题**：原实现先用 `denyPath(pathname)` 判断 URL，再用 `path.join(wwwRoot, pathname)` 落盘。
在 Windows 上，`%5c` 解码后是 `\`，`path.join` 会把 `\..\` 当目录分隔符，而 `denyPath`
只看到 `%5c`/普通斜杠，于是：

```text
GET /foo/%5c..%5cserver/config.js
→ 200，返回 server/config.js
```

同理可读 `server/deploy/credentials.local.json`、`save/online/ssdz.db`、`reference/` 下的
原版素材/源码等。**当前生产**由 Caddy 只反代 `/api/*`、systemd 里 `SERVE_STATIC=false`，
所以线上没有直接暴露；但默认配置、开发机、以及“重新跑部署脚本”都会回到危险状态。

**修复**：新增 `staticPath()`：先拒绝 NUL/盘符/UNC/双斜杠，统一 `\` 为 `/`，用
`path.posix.normalize` 消掉 `.`/`..`，再按**解析后的相对路径**做黑名单与 root 越界检查；
同时把 `/reference/`、`/squirrel_fight_online.exe` 补进拒绝表，静态缓存判断改用规范化路径。

**验证**：本地 `GET /foo/%5c..%5cserver/config.js`、`/reference/`、EXE 均为 404；
`/`、`/index.html`、`/js/state.js` 仍为 200。`tools/test-online-api.cjs` 增加了一条
“编码反斜杠不能绕过静态黑名单”的回归。

### F-02 服务端未设置 `__SSDZ_ONLINE__`，联机经济规则回退（高）

**位置**：`server/game/runtime.js` 的 `installGlobals()`；`js/state.js` 中所有 `ONLINE`
分支（每日任务、新号福利、宝箱重开等）。

**问题**：服务端只设了 `__SSDZ_ONLINE_COMBAT__`，没有设 `__SSDZ_ONLINE__`。`State` 里
`ONLINE=false`，但 `ONLINE_RULES=true`。后果是服务端仍执行单机分支：

- `claimQuest` 可以领每日任务：动态复现中，做一个 `fight` 任务后
  `POST /api/action {"name":"claimQuest","args":[3]}` 返回成功并 `+24` 金松果；
- `claimDaily` 会发“新号前三天”福利：复现中第一天返回
  `gold:250`（100 日常 + 150 新手）和 `大体力药剂 +3`；
- `reopenChest` 使用单机的 500 次上限/含金松果奖池，而不是联机的 10 次/去金池
  （修好 ONLINE 开关后服务端已走联机规则；金宝箱 `pending` 由 `deferSettle` 保留，
  当前三个宝箱动作都可正常执行）；
- `claimApprenticeExp` 的金松果日供也没有被联机规则截断（当前没有收徒入口，暂不可达）。

客户端的 `ONLINE=true` 会让界面看不到这些入口，所以正常玩家不会发现；但改包/直接调
`POST /api/action` 就能领。

**修复**：在 `runtime.installGlobals()` 中设置 `g.__SSDZ_ONLINE__ = true`，让服务端和客户端
使用同一套在线规则。`ONLINE=true` 只影响 `UIMODES`、`save()` 落盘、`load()`、`switchMode`、
每日任务、新号福利、宝箱重开等在线语义；服务端仍是单槽经典、`runOnSave` 直接导出，不受影响。

**验证**：F-02 相关的 `claimDaily`/`claimQuest` 复现已验证：修复后 `claimDaily` 返回
`newbie:null`、首日金松果 100；`claimQuest` 返回 `{ok:false,"没有这个任务"}`。
当前联机经济套件 19/19；API 套件见第 4 节（57/58，失败项为 duplicate 响应的
`integral:0/null` 字段差异，与 F-02 无关）。

> 走 `questState()` 生成题面并落库，客户端只读服务端下发的 `quests`；`claimQuest`
> 仍由服务端校验进度/发奖，不再回退单机随机分支。上面“`claimQuest` 返回没有这个任务”
> 的历史验证已过时；现行断言见 `tools/test-online-api.cjs` 的“每日任务服务端可领取并入 patch”。

### F-03 天梯无 30 级门槛 + 任意快照直连（高）

**位置**：`server/game/fight.js` 的 `runRank()`；`server/api/battle.js` 的 `battle()`。

**问题**：

1. 服务端没有检查等级。1 级账号直接
   `POST /api/battle {"kind":"rank","snapshotId":"s_..."}` 就能开打，获得经验、金杯、积分，
   并计入每日 20 场；客户端/帮助页写的“30 级开启”只是界面拦截。
2. 真实玩家天梯接受任意 `snapshotId`，不要求来自 `/api/opponents` 的候选，也不校验
   等级/积分区间。攻击者可以：
   - 抓一个低等级/低分玩家的快照反复打（每次 +金杯/+积分）；
   - 创建小号，用主号挑小号快照刷胜场/积分；
   - 绕过“最近 5 个对手”的匹配排除。

**修复**：

- 天梯真实对战（非 AI 陪练）先读 `saves.level`，低于 30 返回 409；
- 真实对战优先只接受服务端候选 `o_...`；
- 允许“战报里再次挑战”使用 raw snapshot，但必须同时带 `revengeOf`，且该 `combatId`
  必须是一条真实 rank 战报、对手必须是快照所属账号、攻守双方都可、**同一条战报每人只能用一次**
  （把 `__revenged` 记在旧 `combats.settlement` 里，事务内标记）。

**验证**：

- 1 级 raw rank：409“天梯赛需要达到30级”；
- 30 级 raw rank 不带 `revengeOf`：403；
- 30 级通过候选 ID：200；
- 用真实战报 `revengeOf` 第一次：200；同一战报第二次：403；
- 当前联机 API 套件覆盖了 1 级拒绝、raw 拒绝和候选成功三条路径。

### F-04 周榜同分并列第 1 / 未开打账号白领（中）

**位置**：`server/game/settlement.js` 的 `rankOf()` / `rankAwardStatus()`。

**问题**：原查询只数 `score > mine` 的人数，且不检查是否打过。所有新号注册即 1500 分，
于是**每个 1500 分账号都算第 1 名**，`rankAwardStatus` 的前 100 名门槛失效；金杯商店接入
服务端后，这会直接变成“0 场白领 50 金杯”的经济漏洞。

**当前状态（2026-10-29 后续批次已修）**：`rankOf()` 只统计 `wins + losses > 0` 的账号，
同分按 `wins`、再按 `account_id` 排；0 场账号返回名次 0。`rankAwardStatus()` 额外要求
`played > 0`，`claimRankAward()` 也检查并会提示“先打一场天梯”。`ladder` 同样只列活跃账号。

**验证**：未打过的账号 `rank=0`、`eligible=false`；打过一场后才有名次。当前 API 套件有
“天梯周奖励只发打过天梯的前100名、同周不可重复”用例。

说明：本报告最初复现的是修复前行为（所有 1500 分并列第 1）；该问题在后续经济批次
接入金杯商店时已经收口。

### F-05 好友切磋/留言不校验好友关系（中）

**位置**：`server/game/fight.js` 的 `runFriend()`；`server/api/social.js` 的
`addFriend()` / `leaveFriendMessage()`。

**问题**：

- `runFriend` 可以用任意玩家的 `snapshotId` 发起切磋，不要求好友关系；每次切磋都会给
  对方插一条 `friend_spar` 消息。攻击者可对任意玩家 60 次/分钟刷消息；
- `leaveFriendMessage` 可以给任意 `toId` 留言，不要求好友；
- `addFriend` 不限制**对方**的好友数量，批量小号可以把一个人的好友列表撑到无限大，
  `/api/friends` 的逐行查询会被拖慢。

**修复**：

- 真实玩家切磋要求 `friendships` 中存在双方关系；
- 留言写入要求双方是好友；
- 加好友时检查对方好友数（已存在的好友关系不误伤），上限 `config.friendLimit`。

**验证**：`test-online-api` 里 C 号先与 B 建立好友关系再跑切磋重试；全绿。

### F-06 部署脚本会覆盖安全环境变量（中高）

**位置**：`server/deploy/ssdz-deploy.sh` 生成 systemd unit 的 heredoc。

**问题**：仓库里的 `ssdz-online.service` 有 `SERVE_STATIC=false`、`TRUST_PROXY=true`、
`ALLOW_ORIGIN=...`、`ALLOW_BROWSER_DEVICES=false`；但 `ssdz-deploy.sh` 每次重新生成 unit 时
只写了 `TRUST_PROXY=true`/`ALLOW_BROWSER_DEVICES=false`，没有 `SERVE_STATIC=false` 和
`ALLOW_ORIGIN`。重新部署后：

- Node 静态服务重新开启（虽然 Caddy 仍只反代 `/api`，但本机 3100 端口的暴露面变大；
  一旦有人绕过 Caddy 直连，就是 F-01 的完整源码/存档泄露）；
- CORS 回到默认 `*`；
- 若 `TRUST_PROXY` 也被遗漏，所有请求的 IP 都是 127.0.0.1，登录/注册限流会变成全服共享。

**修复**：把 `SERVE_STATIC=false`、`TRUST_PROXY=true`、`ALLOW_BROWSER_DEVICES=false`、
`ALLOW_ORIGIN=...` 补进部署脚本生成的 unit，与仓库内的 service 文件一致。

### F-07 装备容量只显示不校验（中）

**位置**：`js/state.js` 的 `addGear()` / `composeGear()` / `grantStarterGear()` /
`grantChestReward()` / `applyBlackGearBox()`。

**问题**：`gearCapacity()`（100，VIP +6）只用于界面显示；`addGear` 不检查。玩家可以通过
碎片合成、融合产物、宝箱完整黑装、自选箱、5 级赠装超过容量，从而绕开背包上限，
囤积/出售更多装备。

**修复**：在真正“新增一件装备”的入口先检查容量；融合是 3 件换 1 件（净减少），不拦；
碎片合成/赠装/宝箱装备/黑装自选箱在扣材料前检查，满时返回提示或保留未领取状态。

**验证**：`test-online-economy` 19/19；`test-state` 仍为 104/105（唯一失败是既有的
`backgroundRun` 设置字段与测试期望不一致，与本次改动无关）。

## 3. 未修复 / 需要决策的风险

### R-01 正式服仍是 HTTP 明文（高，用户已接受）

`docs/服务器与部署.md` §1.2 明确记录：443 未放开，正式入口是 `http://111.229.39.217/api/*`。
这意味着同网络（公共 Wi-Fi、代理、运营商链路）可以：

- 直接看到登录密码、`Authorization: Bearer`、`x-device-id`；
- 重放令牌/设备头，冒充账号；
- 修改请求参数（服务端能做语义校验，但账号已经丢了）；
- 篡改服务端响应，让客户端显示假奖励/假战报（只影响本机显示）。

**建议**：能开 443 时优先开；短期至少把登录改成“密码不过网”的挑战-应答，令牌放系统
钥匙串，缩短会话 TTL，服务端支持一键撤销全部会话。不要把“服务端权威”误解成
“明文也安全”：服务端权威防的是改存档，不防账号被偷。

### R-02 设备标识可伪造，一设备一账号不是硬边界（高，残余）

`server/device.js` 只校验 `x-device-id` 的格式，然后对
`platform + '\0' + id` 做 SHA-256；客户端可以随便生成一个 32~128 位字符串，声明
`platform=windows, provider=machine-guid`。`auth.login()` 还会在登录时把新设备直接绑定到账号。
因此：

- 多开小号只需每次换一个假 `x-device-id`；
- 同一台机器换账号不受“一设备一账号”限制；
- 被盗令牌只要连同抓到的设备头一起重放，就能通过会话校验。

文档本身也写了“此机制限制正常客户端多号，不能作为防改包或系统重置的硬件认证”，这个口径
是对的；报告里把它列为**残余风险**，不应在对外文案里承诺“杜绝多开”。

### R-03 免费练习 + 全量存档写入 = 单账号可做磁盘/DB 写放大（高，可用性）

`store.commit()` 每次动作变化都会把整份 `saves.payload` 写回（其中包含最多 50 条完整战斗
记录，当前版本实测存档可达数百 KB）。而下面这些入口**不消耗任何资源、没有每日次数**：

- `runWood`（测攻击木头人）：每次 `recordWoodBattle` + `recordBattle`，改存档；
- `runFriend`（切磋）：每次 `recordBattle`，还会给对方插消息；
- `runRankPractice`（天梯 AI 陪练）：每次 `recordBattle`；
- `setTutorialStep`：可在 1/2 等合法值之间来回切，每次改 `tutorial`；
- `wear` / `unwear`：有装备时可来回切，每次改 `use`。

`actionRatePerMin` 默认 240，战斗 60/min。一个账号就能以每分钟上百次的全量存档写入 +
`action_log` 追加（按 0.3~0.8 MB/次、240 次/分估算，约 70~190 MB/分钟），单账号数小时到
十几小时即可把 59GB 磁盘/WAL 打满，批量小号更快；同时 `action_log`、
`combats`、`messages`、`combat_chests`、`campaign_rooms`、`sessions` 都没有保留清理。
这不是“改属性”的外挂，但属于**单账号可用性攻击**，风险高于普通刷资源。

**建议**（按性价比排序）：

1. 给免费练习入口设独立预算（例如 6~12 次/分钟），或要求消耗一点体力/挑战书；
2. 给“状态写”设每账号的写预算（不是每动作，而是每次落库），超过就拒绝/合并；
3. 把 `battles` 从整档 JSON 移到独立表，或把历史从 50 条降到 10~20 条；
4. 定时清理：`combats` 按 `combatRetentionDays`、`action_log` 按 30~90 天、
   `messages`/`combat_chests`/`campaign_rooms`/`sessions` 按 TTL；
5. `action_log` 只在抽样/异常时写，或写到独立滚动文件而不是主库。

### R-04 天梯互刷/小号仍是主要竞技风险（中高）

本次修掉了“任意快照直连”和“1 级上天梯”，但仍有：

- `/api/opponents` 每 3 秒可刷新（配置 `opponentRefreshCooldownMs` 只返回给客户端，
  服务端没有执行冷却），可以反复挑目标；
- 没有同设备/同 IP/同 ASN 排除；
- 没有“同一对手 N 小时内只能打一次”的硬限制；
- 没有按收益/胜率/操作间隔的行为审计；
- 同设备/同 IP 仍可互刷（R-09 的“0 场白领”已在后续批次修掉，见第 3 节 R-09）。

**建议**：至少把“同设备/同 IP 不互相出现在天梯/随机候选”做成硬过滤；记录固定对手、
交替胜负、异常连胜；周奖励按活跃账号过滤。

### R-05 数据表没有保留/清理策略（中高）

`config.combatRetentionDays` 定义了但代码里没有使用；`security_events` 有惰性清理，
其它表都没有：

- `combats`：每场战斗一行（含完整 result + packet + settlement），20 场/天/人；
- `combat_chests` / `combat_pickups`：每场/每次领取；
- `messages`：每场天梯/切磋/征战都插；
- `action_log`：每个改存档动作一行；
- `sessions`：每次登录一行，过期只在被使用时删除；
- `campaign_rooms` / `campaign_members`：done/expired 后不删除；
- `forum_posts` / `forum_replies` / `friend_messages`：无上限；
- `account_ips`：每账号每 IP 一行，注销才删。

**建议**：部署定时任务（SQLite `DELETE ... WHERE created_at < ?` + `VACUUM`/`wal_checkpoint`），
并把保留天数写进运维文档；否则不是“会不会满”，是“多久满”。

### R-06 读接口无限流，`/api/state` 返回整档（中）

- `/api/state` 返回 `save`（含 `battles` 50 条）、`snapshot`、`summary`，没有限流；
- `/api/friends` 最多 50 个好友，每个好友 4 次 DB 查询（N+1），没有限流；
- `/api/fighter` 可按 `accountId`/`snapshotId` 取任意玩家面板，没有限流；
- `/api/opponents`、`/api/campaign/bosses`（会触发 `pump()`）、`/api/campaign/current`
  也没有专门的写/CPU 预算。

**建议**：至少对 `state/friends/fighter/campaign` 加每账号读限流；`/api/state` 改成
“登录时拉整档，之后只拉 patch/summary”，或把 `battles` 分页；对 `fighter` 收窄到
“候选/好友/战报相关账号”。

### R-07 账号口令策略偏弱（中）

- `normalizePassword` 只要求 4 位，允许 128 位；没有常见口令黑名单；
- `login` 限流按 IP（30/min），没有按账号锁定/指数退避；
- 登录错误区分“没有这个账号”/“密码不对”，可枚举账号；
- 注册 6/hour/IP，恢复 10/hour/IP；
- 正式服是 HTTP，撞库/窃听叠加。

> **2026-11-05 更新**：口令下限已改为“至少 6 位且同时包含字母和数字”（注册 / 恢复 / 修改密码共用）；常见口令黑名单、按账号锁定、统一错误文案仍待办。

**建议**：最少 8 位、常见口令黑名单、按账号+IP 双维度限速、统一“账号或密码不对”文案；
管理后台/封禁走本地 CLI（已有 `admin-audit.js`），不要把管理接口暴露成 HTTP。

### R-08 客户端完整性与 token 存储（中）

- Tauri `tauri.conf.json` 的 `security.csp` 是 `null`；
- EXE 内 `js/` 可解包阅读/修改；`js/debug.js` 也在构建快照里（未被 `index-online.html`
  加载，但解包后可以自行加载）；
- token 存在 `localStorage`（`ssdz-online-token`），没有系统钥匙串；
- 没有客户端版本/签名/设备完整性上报，`x-client-version` 只在 CORS 允许列表里，服务端未校验；
- 没有 sourcemap/混淆不等于安全，但会增加改包成本。

**建议**：加 CSP（至少 `default-src 'self'; connect-src ...`）、把 token 放系统钥匙串、
服务端记录并拒绝明显过旧的客户端版本；不要把这些当反作弊主防线。核心仍是 F-02/F-03
这类服务端规则。

### R-09 周奖励没有活跃门槛（中）

`rankOf()` 现在同分有唯一名次，但**0 胜 0 负的新号仍会进入排名**。前 100 个注册账号可以
不玩就领每周 50 金杯（当前金杯商店未接入服务端，暂时不能变现；接入后就是经济漏洞）。

**建议**：`rankOf`/`rankAwardStatus` 只统计 `wins + losses > 0` 的账号，或周奖励领取时
要求至少完成 1 场天梯。

**2026-10-29 已修**：`rankOf`/`ladder`/`rankAwardStatus` 只统计 `wins + losses > 0` 的账号，
周奖励领取额外要求 `played > 0`；0 胜 0 负的新号不再进入排名。

### R-10 社交骚扰面（中低）

- `addFriend` 仍是“单向添加、双向写入”，不需要对方同意；本次只限制了对方好友上限；
- `friendMessages` 的 GET 仍可读任意账号的留言板（不要求好友）；
- `forum` 对全体登录用户可见，发帖 5/min、回复 20/min；
- 切磋消息只对好友了，但好友仍可 60/min 刷；
- 没有拉黑/举报/屏蔽。

**建议**：好友申请 + 接受/拒绝、拉黑、举报；留言板读也按好友收口；给消息表做 TTL。

### R-11 侦察面过大（中低）

- `/api/fighter?accountId=` 可按连续账号 id 枚举任意玩家的等级、四维、装备、幻兽、武技；
- `/api/fighter?snapshotId=` 可拿任意历史快照；
- `/api/board?accountId=` 可读任意留言板；
- `/api/players?q=%` 可枚举账号；
- `/api/check-name` 可枚举名字/tag。

这些不直接改数据，但让选目标、针对换装、社工更容易。**建议**：只对“候选/好友/战报相关”
账号开放完整面板，其它只返回摘要；对搜索/侦察接口限流。

### R-12 小问题清单（低）

- `config.rankIntegralCap`、`rankIntegralTiers`、`opponentRefreshCooldownMs`、
  `combatRetentionDays`、`campaignDiceMax`、`campaignHouseCut` 等配置没有被使用，易造成
  “文档/配置说有一套、代码没执行”的误判；其中 `integralDelta()` 还硬编码了
  `<100 / <300 / <1000` 三档，和 `rankIntegralTiers` 的 `1000 / 1500` 不一致，
  建议确认天梯积分表到底以哪套为准；
- ~~`claimRankAward` 先插 `rank_awards` 再 `runOnSave` 加金杯，不在同一事务：中途失败会
  “奖励记录已用、金杯没到”~~（2026-10-29 已修：合并进同一 `db.tx`）；
- ~~在线版 `beginChest` 之后，下一次动作的 `restorePayload` 会先把 `chestPending` 自动结算，
  所以 `confirmChest`/`reopenChest` 这两个动作在服务端实际拿不到 pending；`reopenChest`
  的联机 10 次上限也因此不可达（功能问题，不是刷资源）~~（2026-10-29 已修：宝箱动作以
  `deferSettle` 读档，pending 保留到领取/重开）；
- `runFriend` 的 `friend_spar` 消息、`leaveFriendMessage` 的留言都没有 TTL；
- `observeIp`/`bind`/`touchSession` 每个认证请求都写 `accounts.ip`、`account_ips`、
  `account_devices`、`sessions`，进一步放大 R-03 的写放大；
- `matchPath` 对非法 `%` 会 `decodeURIComponent` 抛错，返回 500，可被用来刷日志；
- 注册同名 tag 兜底 `COUNT+1` 在极端情况下可能与已有 tag 冲突，返回 500；
- `normalizeName` 允许 `#` 和双向控制字符，存在名字伪装/`名字#编号` 歧义；

- 静态目录默认 `wwwRoot=仓库根`，且 `serveStatic` 默认是 `true`；生产必须保持

## 6. 边界说明

本报告只覆盖**当前工作区代码**，不覆盖：

- 线上机器本身的 SSH/云安全组/系统补丁/备份；
- 用户自己的账号密码是否在别处泄露；
- 客户端 EXE 被本机管理员级恶意软件控制的场景（那种情况下任何客户端校验都不可信）；
- 原版素材/参考目录的版权与分发问题。

可伪造设备头、刷分小号和写放大/无清理，这些都不是靠客户端加壳能解决的。**
