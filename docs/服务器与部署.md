# 服务器与部署（本机凭据记录）

## 本机全服奖励邮件（金松果 / 金杯 / 道具）

在服务器上创建一个仅供本机操作者使用的 UTF-8 JSON 文件，例如
`{"id":"event_20261103_01","text":"活动奖励","gold":100,"cup":5,"props":{"23":2,"36":1}}`：

- `gold` = 金松果（`goldPoint`），`cup` = 金杯（`goldCup`），都可省略或设为 0；
- `props` = `{"道具id": 数量}`，数量 1–9999；`8/15/40` 是货币/经验，必须走 `gold` / `cup`，不能写进 `props`；
- **奖励不是发放即到账**：命令只写一封 `announcement` 邮件（`payload.claimable=true`）。玩家在消息页「消息」tab 点开它，小弹窗列出具体奖励，点「领取」后由 `POST /api/messages/claim` 入账；同一封邮件只能领一次。老公告（没有 `claimable`）仍然只是通知，不会出现领取入口；
- 每次活动必须使用新的 8–80 位字母、数字、下划线或连字符编号；同编号同内容可安全重试（不会重复写邮件），同编号不同内容会拒绝；发放对象是执行时未封禁且有经典存档的账号，之后注册的账号不追溯；
- 邮件一旦写入不能通过该命令撤回；文案最多 200 字，奖励清单由命令自动追加在正文后。

执行（以能写 `/var/lib/ssdz` 的服务账号）：

```bash
sudo -u ssdz env DATA_DIR=/var/lib/ssdz GAME_ROOT=/opt/ssdz \
  /opt/node22/bin/node /opt/ssdz/server/admin-broadcast.js /path/to/event.json
```

输出 `{"duplicate":false,"recipients":N}` 只表示邮件已写入（奖励尚未入账）；可再用只读脚本查 `admin_broadcasts`、`messages` 与玩家领取后的 `claimedAt`。工具只在本机 CLI 运行，没有公开管理 HTTP 接口。

### 开服 / 新玩家奖励邮件（按等级自动投递）

`server/game/server-mail.js` 的 `TEMPLATES` 是**常驻规则**，不是一次性广播。每个模板带一个
`enabled` 激活开关，**只认显式 `true`**；现在开服奖励模板是 `enabled: false`（停用），部署后
**一封都不会发**。确认文案/奖励无误后把它改成 `true` 再部署，才开始投递：账号等级达到模板的
`minLevel` 后，`GET /api/state`（登录/重连）或 `GET /api/messages`（打开消息页）会自动写一封待领取
邮件，id 固定 `servermail:<模板id>:<账号id>`，重复投递不会写第二条。默认模板是 **2 级**（消息功能解锁）
的开服奖励，所以打开后新玩家升到 2 级、打开「消息」页就能看到并领取；当时已有的 2 级以上账号也会在
下一次登录/开消息页时各收到一封。

- 改文案 / 奖励 / 等级门槛 / 开关：只改 `server/game/server-mail.js` 后重新部署（纯服务端改动，老客户端也能领）；
- 关掉（撤回）只需把 `enabled` 改回 `false`：已发出去的邮件仍可领取，不会被回收；
- 再发一轮：换一个模板 `id`（每个账号各收到新 id 的一封）。只想发给某时间之后注册的账号，给模板加
  `registeredAfter: Date.parse('2026-11-06T00:00:00+08:00')`（不填 = 所有账号各一封）；
- 一次性全服公告 / 活动奖励仍用上面的 `admin-broadcast.js`（有 `admin_broadcasts` 台账、不追溯新号）。

> 这一页是给**本机上的 agent 会话**看的：新开一个窗口时不需要用户再重复告知服务器密码。
> 凭据本体在 `server/deploy/credentials.local.json`（已被 `.gitignore` 忽略，不进版本库）。

### 3.1.1 创作者设备白名单（服务器主人自用）

给“只允许我的设备批量建测试号”的场景用。**按设备指纹认，不按 IP**：IP 会被 NAT / 动态地址影响，
无法保证“只有我的设备”。白名单里的设备可以：

- 使用 `browser` / `installation` 设备标识（普通设备仍被 `ALLOW_BROWSER_DEVICES=false` 拒）；
- 绕过注册总名额（`REGISTRATION_LIMIT`，默认 **1000**，0 表示不限）与注册限流（6 次/小时/IP）；
- 一台设备建多个账号（普通设备最多 3 个），且不受 `ACCOUNTS_PER_DEVICE` / `ACCOUNTS_PER_IP` 限制；
- 设置页「开发者同步」也按这张表确认主人（默认还要命中 `OWNER_IPS`）；普通设备即使同 IP 也看不到；
- **仍受**同一 IP 每天注册 / 注销各 5 次的日限（`ACCOUNT_DAILY_LIMIT`）；需要批量建测试号时把该变量设为 0 关闭整道闸。登录/找回仍保留限流。

做法：

```bash
# /etc/ssdz/creator.env（root 600）——值是 sha256(platform + '\0' + rawId)，逗号分隔
CREATOR_DEVICES=<64 位 hex>,<64 位 hex>
# systemd 单元已带 EnvironmentFile=-/etc/ssdz/creator.env
```

新服迁移时已从旧服原样复制 `/etc/ssdz/creator.env`。浏览器本地页要连**线上** API 时，把
`http://127.0.0.1:5896` / `http://localhost:5896` 加进 `ALLOW_ORIGIN`（单元里已含）。
加一台设备：让它先发一次登录/注册请求（失败也会在 `security_events` / `account_devices`
留下 `device_hash`），把该 hash 追加到 `creator.env`，`systemctl restart ssdz-online`。
浏览器测试端可以用 `localStorage['ssdz-online-browser-device'] = '<64 位 hex>'` 指定固定 ID
（客户端会拒绝非 64 位 hex 的值）；原始 ID 是凭据，不要写进仓库或贴给别人。

### 3.1.2 自动备份

服务端启动时、之后每 `BACKUP_INTERVAL_MS`（默认 6 小时）自动调用 SQLite
`VACUUM INTO` 生成一致性快照，写到 `DATA_DIR/backup/auto/ssdz-YYYYMMDD-HHmmss.db`。
生成后先做 `PRAGMA integrity_check`，通过才原子改名；默认保留 7 天、最多 56 份，
只清理这个 auto 子目录，不碰 `backup/`、`backups/` 里的人工副本。

环境变量（可选）：

```ini
BACKUP_ENABLED=true
BACKUP_INTERVAL_MS=21600000
BACKUP_RETENTION_DAYS=7
BACKUP_MAX_FILES=56
# BACKUP_DIR=/var/lib/ssdz/backup/auto
```

恢复时先停服务，把备份 `cp` 到 `$DATA_DIR/ssdz.db`（同时清掉 `ssdz.db-wal`/`-shm`），
`chown ssdz:ssdz`、`chmod 600`，再启动并检查 `/api/health`。不要直接复制正在写的
`ssdz.db + -wal` 当备份；手工备份也建议用 `VACUUM INTO`。

### 3.1.3 反向拉包部署（服务器来本机拉，可选）

本机不需要有公网入口：起一个只绑回环的静态服务，再开 SSH 反向隧道，服务器就能用 `curl`
把包和部署脚本拉到自己的 `/tmp`（2026-11-06 实测发过一版，1.75 MB）：

1. 本机打包到 `out/`，然后 `python -m http.server 18080 --bind 127.0.0.1 --directory out`；
2. 本机开反向隧道（任选其一）：`ssh -R 18080:127.0.0.1:18080 ubuntu@140.143.142.110`，
   或脚本里用 Paramiko `transport.request_port_forward('127.0.0.1', 18080, handler)`
   （handler 把转发进来的连接接到本机 18080）；
3. 服务器上：
   `curl --noproxy '*' -fsS http://127.0.0.1:18080/ssdz-api.tgz -o /tmp/ssdz-api.tgz` →
   `sha256sum` 与本地比对 → 同样 `curl` 下 `ssdz-deploy.sh` → `bash /tmp/ssdz-deploy.sh /tmp/ssdz-api.tgz`；
4. 断开隧道、关掉本机静态服务。

隧道端口只绑服务器回环，公网看不到；包和部署脚本都能走同一条隧道。

### 3.2 客户端怎么找到服务器

`js/net.js` 的 `discover()`：

1. 候选地址 = 用户手填（`localStorage['ssdz-online-base']`）→ 安装包 `__SSDZ_ONLINE_API__`
   → 安装包 `__SSDZ_ONLINE_API_FALLBACKS__` → 网页同源；
2. 上次成功的地址先单独试 900 ms（冷启动 ~1.5 s，热启动 ~90 ms）；
3. 都不行就把**每一个试过的地址和失败原因**写进错误消息，登录页直接显示出来；
4. 跑在 http 上时后台再探一次 https，通了就静默切过去（只适用于有 https 的地址）。

当前安装包地址：`src-tauri/online-api.json` 的
`{"base":"http://140.143.142.110:5896"}`。构建脚本 `tools/build-online-app.cjs` 对 5896
这种非 80/443 端口**不会派生 https fallback**，避免每次冷启动白等一条失败的 TLS 探测。

构建时改地址：`tools/build-online-app.cjs --api http://<host>:5896`，或改
`src-tauri/online-api.json` 的 `base`（还支持 `fallbacks` 数组）。改完必须重新生成
`src-tauri/web` 快照并重打 EXE；Android 的 cleartext 白名单由
`tools/build-online-apk.cjs` 从同一份 base 自动生成，APK 需重新打包才会生效。

### 3.2.1 客户端更新提示与下载页（1.0.28 起）

- `GET /api/update` 的版本号取服务器上的 `scripts/version.json`；`server/update.json` 只控制
  `notes / url / force / minVersion / pollSeconds`。客户端 `js/online-update.js` 每 `pollSeconds`
  （默认 60，最小 20）比对一次，本地 `__SSDZ_VERSION` 更低就弹窗；**1.0.23 之前的客户端没有这个轮询**。
- **自动弹窗只通知，不下载**：发现新版本只给「前往设置 / 知道了」（强制更新为「前往设置 / 复制下载地址」），
  不会自动打开下载页、整包替换或下载 APK/IPA。唯一允许从服务器下载整包的入口是
  「设置 → 联机账号 → 检查更新」；界面会提示优先加入 QQ 群 **1128710765** 下载最新版本。
- 下载页 `GET /download`；安装包放 `DATA_DIR/downloads/`（`ssdz` 可读、`644`），
  `GET /download/<文件名>` 直接下发，只收 `.exe/.apk/.ipa/.dmg/.zip`，文件名不允许路径分隔符。
  `SERVE_STATIC=false` 不影响这两个入口。
- 发版顺序：**先把新包放进 downloads，再部署带新 `scripts/version.json` 的服务端包**，
  否则玩家先看到提示、下载页还是空的。自动弹窗普通更新只有「前往设置 / 知道了」，`force=true` 或
  `minVersion` 高于本地版本时锁窗（只有「前往设置 / 复制下载地址」），都不会直接下载。
- **保留策略**：`downloads` 只留当前版本（`scripts/version.json`）的五个包；`ssdz-deploy.sh`
  部署末尾自动删除旧版本包（`manifests/` 除外），旧直链随包失效。本地 `src-tauri/dist` 同样
  只留当前版本（`tools/prune-dist.cjs`，出包后自动调用）。
- 1.0.56 起设置 → 联机账号也有「检查更新」；设置页的更新框才出现「从服务器更新 / 稍后再说」，
  点「从服务器更新」后 Windows 完整包走 `online_sync_client` 整包替换；
  Android 按 `Build.SUPPORTED_ABIS` 选 `apk`（arm64）或 `apkX86`，下载后打开系统安装器
  （manifest 需 `REQUEST_INSTALL_PACKAGES`，用户还要在系统里允许安装未知应用）。
  `/api/update` 同时下发 `exe/apk/apkX86/ipa/ipaLegacy` 与大小，发布时对应包都要放进 downloads。
- 纯网页端「设置 → 游戏设置」有「下载客户端」：浏览器识别本机系统 / 架构后请求
  `GET /api/client/download?os=<windows|android|ios|macos|linux|chromeos>&arch=<x64|x86_64|arm64|x86|arm>&ios=<大版本>`，
  服务端按 `owner.packageInfo` 选包（Android 分 arm64 / x86_64，iOS 26+ 用默认包、15~25 用 legacy）；
  该平台没有包时返回 `reason` 与 `downloadPage`，网页只给「打开下载页」，不会下别的平台安装包。
- iOS（越狱 / TrollStore）：iOS 客户端请求 `/api/update` 时，服务端按请求头 `x-device-platform: ios`
  返回 **iOS 最新 IPA 的版本**（当前 1.0.62），不会拿 EXE/APK 的 1.0.63 反复提示 iOS 用户。
  `ipa` 指向当前 iOS 版本 `squirrel_fight_online_<版本>_ios_unsigned.ipa`，`ipaLegacy` 指向
  `..._ios_legacy_unsigned.ipa`；没有对应版本时退回 downloads 里最新的 iOS 包，并下发
  `ipaVersion` / `ipaLegacyVersion`。客户端按 UA 的系统版本选择（iOS 26+ 默认包，iOS 15~25 legacy）。
  设置页点「从服务器更新」只打开对应 IPA 的下载地址（系统浏览器 / Files），由 TrollStore、AltStore
  或 Sideloadly 安装；游戏不尝试原地替换 App 包。保持同一 Bundle ID（`com.ssdz.online`）时服务器
  账号与进度不受影响。两个 IPA 由 `node tools/build-online-ios.cjs` 产出到 `src-tauri/dist`，发版时上传：
  `sudo install -o ssdz -g ssdz -m 644 <ipa> /var/lib/ssdz/downloads/`。

### 3.3 设备绑定与 IP 监控（1.0.2 起）

正式服：同一设备 / 同一 IP 最多**创建** 3 个账号（`ACCOUNTS_PER_DEVICE` / `ACCOUNTS_PER_IP`，IP 设为 0 可只限设备）；同一 IP 每天最多**注册 5 次、注销 5 次**（`ACCOUNT_DAILY_LIMIT`，默认 5，0 表示关闭；两项分开计数，按 `Asia/Shanghai` 次日 0 点重置；对所有设备生效）；登录已有账号不占创建额度，同一账号只保留一个在线会话，后登录会顶掉旧设备（旧设备提示 `SESSION_KICKED`）。同一账号可以绑定多台设备。
退出登录不会解除设备绑定，注销账号会删除该账号的设备绑定。旧客户端缺少设备头，不能继续推进进度，需升级。
Windows 使用本机系统标识的散列，Android 使用应用签名/系统用户范围的 Android ID 散列，iOS 使用本机 Keychain 值的散列。
服务器再作散列保存，不保存原始系统标识。此机制限制正常客户端多号，不能作为防改包或系统重置的硬件认证。

部署的 systemd 环境必须包含：

```ini
Environment=TRUST_PROXY=false        # 新服 5896 是直连；若以后放到反代后面再改 true
Environment=SERVE_STATIC=true        # 纯网页端：Node 直接下发 /、/play 与静态素材
Environment=ALLOW_BROWSER_DEVICES=true   # 浏览器安装标识可注册/登录；关闭后网页登录被拒
```

`TRUST_PROXY` 仅在连接来自本机反向代理时信任转发头，避免将公网用户的伪造头当作真实 IP。
正式服拒绝浏览器/随机安装标识；开发机需要浏览器联调时才显式设置 `ALLOW_BROWSER_DEVICES=true`。

服务器记录注册、登录及会话校验的成功/失败、设备绑定和 IP 变化；同 IP 多账号仅列作关联线索，不自动封禁家庭/校园共享网络。
安全事件默认按 90 天惰性清理（`SECURITY_RETENTION_DAYS`）；账号 IP 映射保留至账号注销。
管理查询只允许通过服务器本机 CLI，不提供公开管理 API：

```bash
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-audit.js --days 7 --limit 30
# 仅看某账号（也可使用数字账号 ID）
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-audit.js --account '名字#编号'
# 仅看指定 IP 的关联与事件
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-audit.js --ip 127.0.0.1
```

### 3.4 查看注册玩家与库存（只读）

`server/admin-players.js` 直接以只读方式打开 `ssdz.db`（不启动游戏服务、不写库，可在服务运行时执行）。
本机最省事的是 `server/deploy/admin-players.py`（读本机 `credentials.local.json`，走 Paramiko，不手敲 ssh 密码）：

```powershell
python server/deploy/admin-players.py --all
python server/deploy/admin-players.py --player 6
```

服务器上也可直接跑：

```bash
# 玩家表（默认前 200 个）+ 全服常见物品合计
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-players.js
# 所有账号 / 单个玩家完整背包 / 按昵称或 ID 过滤
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-players.js --all
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-players.js --player 6
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-players.js --search 鼠
# 机器可读（给表格/脚本用）
sudo -u ssdz env DATA_DIR=/var/lib/ssdz /opt/node22/bin/node /opt/ssdz/server/admin-players.js --all --json > /tmp/players.json
```

- 本机 launcher 需要 `paramiko`（本机已装；缺了会提示 `python -m pip install paramiko`）。
- 默认统计 **道具库存**（ID + 名称 + 数量 + 持有人数）、装备数、武器/技能/幻兽数、建筑、金松果/金杯/积分、VIP、注册/最后在线、封禁/模拟/开发标记。
- `--db <文件>` 可看本机拷贝或备份；不加时依次找 `DATA_DIR/ssdz.db`、`/var/lib/ssdz/ssdz.db`、仓库 `save/online/ssdz.db`。
- 物品名来自 `js/gamedict.js` + `js/gamedata.js`；这两个文件缺失时退化为 `道具#ID`，数量仍准确。

输出包含账号/IP 关系、设备平台与短散列、近期事件及同 IP 多账号摘要，不包含密码、会话令牌或原始设备 ID。
